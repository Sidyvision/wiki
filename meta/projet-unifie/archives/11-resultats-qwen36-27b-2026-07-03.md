## 3. Corrections apportées aux règles de la v2 (`09-…v2`)

Deux règles de la v2 se sont révélées **fausses ou incomplètes** à l'usage. Elles sont corrigées
dans la version révisée du briefing 09 (jointe à ce lot).

### 3.1 `sleep infinity` NE fonctionne PAS comme Container Start Command

La v2 (§5, étape B) prescrivait `sleep infinity` pour obtenir un conteneur dormant. **Faux** :
l'image `vllm/vllm-openai` a pour ENTRYPOINT fixe `vllm serve`. Tout ce qui est saisi dans le
champ « Container Start Command » est **appendé comme arguments** à cet ENTRYPOINT. Résultat
observé :
- `sleep infinity` → exécuté comme `vllm serve sleep infinity` → `unrecognized arguments: infinity`
- `;sleep infinity` → exécuté comme `vllm serve ;sleep infinity` → le `;` est un argument littéral,
  pas un séparateur shell → process en **échec permanent à 167 % CPU**, cause des coupures SSH.

**Recette correcte (validée le 2026-07-03)** : le champ ne doit contenir **que les arguments** de
`vllm serve`, en commençant directement par le nom du modèle — exactement le format déjà présent
dans le compte-rendu Ornith `06-…` (« la commande de démarrage finale commençait par le nom du
modèle, sans `vllm serve` devant ») :

```
Qwen/Qwen3.6-27B-FP8 --served-model-name Qwen3.6-27B-FP8 --host 127.0.0.1 --port 8000 --max-model-len 131072 --gpu-memory-utilization 0.90 --enable-prefix-caching --enable-auto-tool-choice --tool-call-parser qwen3_coder --reasoning-parser qwen3 --trust-remote-code
```

Avec `HF_HOME=/workspace/huggingface` posé en variable et le modèle déjà en cache, vLLM le charge
sans re-télécharger. Le modèle démarre seul au boot du Pod → plus besoin de lancement manuel une
fois la config validée (l'étape « pérenniser » de la v2 devient le mode nominal).

### 3.2 Régression Claude Code ≥ 2.1.154 (nouveau piège, bloquant)

Depuis la version **2.1.154**, Claude Code injecte un bloc `role: "system"` **dans le tableau
`messages[]`** au lieu du champ `system` séparé, en violation de la spec Anthropic. L'endpoint
`/v1/messages` de vLLM (qui valide correctement) rejette alors toute requête :

```
API Error: 400 — messages[1].role: Input should be 'user' or 'assistant', input: 'system'
```

Confirmé comme bug amont de Claude Code (issue `anthropics/claude-code#63469`), reproduit sur
l'API Anthropic officielle et sur tous les endpoints tiers stricts (vLLM, GLM…). La version
affichée pendant la session était 2.1.198, bien au-delà du seuil.

**Correctif appliqué** :
```bash
npm install -g @anthropic-ai/claude-code@2.1.150
```
+ **désactiver l'auto-update** (sinon npm/claude remonte seul en dernière version — observé en
séance) :
```bash
export DISABLE_AUTOUPDATER=1
```

> Nota important pour Hermes (briefing 10) : Hermes parle à vLLM via l'endpoint
> **OpenAI-compatible** (`/v1/chat/completions`), pas l'endpoint Anthropic `/v1/messages`. Il
> **n'est donc pas affecté** par ce bug. Le pin de Claude Code à 2.1.150 est un correctif
> transitoire pour les Phases 1-5 (double exécution), qui disparaît à la bascule Phase 6.

## 4. Autres pièges RunPod confirmés le 2026-07-03

- **Volume chiffré non redimensionnable** : `Encrypted volume cannot be resized`. Toujours
  décocher « Encrypt volume disk » à la création — sinon il faut recréer le Pod.
- **Proxy `ssh.runpod.io` instable** : sessions coupées en quelques secondes de façon aléatoire.
  Contournements : lancer les opérations longues en arrière-plan détaché
  (`nohup … & disown`), et privilégier la **connexion TCP directe** dès que `sshd` est posé (plus
  stable que le proxy).
- **Quota disque selon datacenter** : certains montages `/workspace` exposent un quota strict (50
  Go), d'autres un NFS de plusieurs centaines de To. Ne pas se fier au `df -h` du montage
  sous-jacent ; le quota effectif est celui du « Volume disk » configuré.
- **Format de cache HF** : `hf download Qwen/Qwen3.6-27B-FP8` **sans** `--local-dir` (dépôt en
  `models--Qwen--Qwen3.6-27B-FP8/`, seul format lu par vLLM). Le format plat `--local-dir` n'est
  pas reconnu.
- **Diagnostic OOM** : au premier « Free memory » anormal, lancer `ps aux | grep -i vllm` et
  `nvidia-smi` AVANT de changer de matériel. La cause du 02-07 était un process fantôme du
  template, pas un GPU défaillant.
